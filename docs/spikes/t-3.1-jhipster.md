# T-3.1 spike: what JHipster actually generates

**Date:** 2026-08-20 · **Generator:** `generator-jhipster@9.2.0` · **Verdict:** GO, with named deletions

Run against [`services/xenopsbase.jdl`](../../services/xenopsbase.jdl), generating a gateway and one
core service with OIDC and Postgres. Everything below was observed, not read from documentation.

## Verdict

**Use it to scaffold, then detach — which is what [T-3.4](https://github.com/mertkan-iscan/xenopsbase-stemcell/issues/27) already assumed.**

JHipster earns its place on a narrow set of things that are genuinely fiddly and easy to get subtly
wrong. It loses on everything that overlaps the platform already built, and that overlap is larger
than expected.

## What is worth keeping

| What | Why it is worth having |
|---|---|
| `config/SecurityConfiguration` | OIDC resource-server + client wiring that works against the Keycloak realm from T-2.5 |
| `security/oauth2/AudienceValidator` | Validates the `aud` claim. Omitting this is a real vulnerability, and it is the kind of thing that is forgotten because nothing fails without it |
| `web/rest/errors/*` | RFC 7807 problem-details translation — exactly what [T-3.8](https://github.com/mertkan-iscan/xenopsbase-stemcell/issues/31) asks for |
| `web/filter/OAuth2ReactiveRefreshTokensWebFilter` | Refresh-token handling, fiddly to write correctly |
| `config/CRLFLogConverter` | Strips CR/LF from logged values — log-injection defence most projects never add |
| `config/OpenApiConfiguration` | springdoc setup, [T-3.11](https://github.com/mertkan-iscan/xenopsbase-stemcell/issues/34) |
| `pom.xml` | A curated, mutually-compatible dependency set with Spring Boot 3.5.15 |

## What gets deleted, and why

**Everything under `src/main/docker/` — 13 files.** JHipster ships its own `grafana/`,
`prometheus/`, `keycloak.yml`, `realm-config/`, `zipkin.yml`, `sonar.yml`,
`jhipster-control-center.yml` and `postgresql.yml`. Every one of those duplicates something already
running in the cluster, configured differently. Keeping them would mean two Keycloak realms and two
Prometheus configurations, and the wrong one would eventually be edited.

**The gateway's local user model — 20 classes.** `User`, `Authority`, `UserRepository`,
`UserSqlHelper`, `UserMapper`, the DTOs, `AccountResource`, `PublicUserResource`,
`AuthorityResource` and the Liquibase tables behind them.

JHipster's OAuth2 gateway mirrors Keycloak users into its own `jhi_user` table. **Keycloak is the
identity provider** (T-2.5); a second user store is a competing source of truth, and the failure
mode is silent divergence rather than an error.

`--skip-user-management` **does not remove it.** Measured: the flag drops 2 files and leaves all 20
user classes in place. Deleting them is manual surgery, and that work belongs in T-3.4.

**Liquibase configuration and changelogs.** See the conflict below.

## Conflicts found

### 1. JHipster is Liquibase-only; T-3.6 asks for Flyway

`databaseMigration flyway` is rejected by the JDL parser, and the string `flyway` does not appear
anywhere in the generator. Only `'liquibase'` exists.

[T-3.6](https://github.com/mertkan-iscan/xenopsbase-stemcell/issues/29) specifies a Flyway baseline
with `ddl-auto: validate` from the first commit. **These cannot both stand.** Either T-3.6 changes to
Liquibase, or the generated Liquibase wiring is replaced during T-3.4.

Not decided here — it changes a written commitment.

### 2. The gateway is reactive; the core is not

The generated gateway is WebFlux + R2DBC + `spring-cloud-starter-gateway-server-webflux`. The core
service is servlet + JPA.

That is defensible — a gateway is I/O-bound and proxies, which is what reactive is for — but it means
**two programming models in one template**: different debugging, different testing, no blocking JDBC
in the gateway. Anyone forking this inherits both. Worth stating loudly rather than discovering at
the first `block()`.

### 3. Java version

Generated poms target **21**. JHipster declares `JAVA_COMPATIBLE_VERSIONS = ['21', '25']` and has no
JDL option or CLI flag to choose — but changing `<java.version>` is a one-line edit and **both apps
compile clean on 25**:

```
core     BUILD SUCCESS   37 source files   JDK 25.0.10
gateway  BUILD SUCCESS   61 source files   JDK 25.0.10
```

25 is the current LTS, so this is the newer of the two the generator actually supports rather than
the newest that exists — a JDK the generator cannot reason about is a worse trade than one release
of lag.

## Scale

```
gateway   152 files    947K
core      116 files    755K
```

Roughly **33 of 268 files are the reason to use the generator**. That ratio is the argument for
scaffold-then-detach rather than treating JHipster as a dependency: it is a good first commit and a
poor long-term owner.

## If it had been a no-go

The fallback is Spring Initializr with `web`, `security`, `oauth2-resource-server`, `oauth2-client`,
`data-jpa`, `postgresql`, `flyway`, `actuator`, `validation`, plus Spring Cloud Gateway for the
gateway — then writing the security config, audience validation and problem-details handling by
hand. That is maybe two days of work, most of it in the OIDC wiring, and it is the part JHipster
gets right.

Recorded so the fallback is a decision rather than a rewrite if the conflicts above turn out worse
than they look.
